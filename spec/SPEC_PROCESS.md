## 二、关键决策节点

### 节点 1：语言选择

**问题**：四种候选语言（TypeScript、Go、Rust、Python）选哪个？

| 语言 | 提议方 | 理由 |
|------|--------|------|
| TypeScript | AI 建议 | 生态丰富，LLM SDK 支持好，适合 CLI |
| Go | AI 建议 | 编译为单二进制，并发模型好 |
| Rust | AI 建议 | 最高性能，类型安全，但学习曲线陡 |
| **Python** | **学生选定** | 生态最丰富，开发速度快，pytest 成熟 |

**决策**：选择 Python。理由：项目需要快速迭代、Mock LLM 测试简单、pytest 生态成熟、openai SDK 支持好。

**学生修正**：AI 最初倾向于 TypeScript 或 Go，但学生明确选择了 Python，理由是"生态最丰富，LLM SDK 最多，开发最快"。

### 节点 2：深入维度选择

**问题**：治理/护栏（A）还是反馈回路（B）？

**AI 建议**：推荐治理/护栏，因为它天然适合用代码实现，每条拦截规则都可以写确定性单元测试。

**学生决策**：选择 A（治理/护栏）。

**理由**：四层状态机（围栏 → 分级 → HITL → 沙箱）构成了完整的防御纵深，最符合作业"移除 LLM 后仍可验证"的核心判据。

### 节点 3：LLM 提供商选择

**问题**：Anthropic、OpenAI、本地模型，还是多提供商？

**AI 建议**：推荐 Anthropic（与开发工具 Claude Code 一致）。

**学生提出**：使用中转站 API，兼容 OpenAI 格式，支持工具调用。

**决策**：OpenAI 兼容中转站 API。学生提供了具体信息（中转站 API base URL、模型名），由学生在 `harness.yaml` 中自行配置。

### 节点 4：分发方式

**问题**：Docker 还是 PyPI？

**AI 建议**：两者都做，覆盖面广。

**学生决策**：PyPI 包。理由：pip install 最自然，轻量。

### 节点 5：WebUI 设计

**问题**：WebUI 的形态？

| 形态 | 说明 |
|------|------|
| 简单 Web 仪表盘 | AI 推荐，CLI 为主 |
| 完整 Web IDE | 工作量太大，否决 |

**决策**：CLI 为主 + 简单 Web 仪表盘。部署到阿里云 ECS（学生指定）。

## 五、Brainstorming 技能评价

### 做得好的地方
1. **追问机制**：技能主动追问设计决策而非一次性抛出所有问题，每轮一个问题，控制认知负荷
2. **多方案对比**：在语言选择、深入维度、方案设计等节点都提供了 2-3 个选项及权衡分析
3. **渐进式确认**：每展示一个设计小节就请用户确认，避免了"全部设计完才发现方向不对"的情况

### 不足之处
1. **过度假设**：AI 默认了几个假设（如 Vercel 部署、TypeScript 偏好），需要学生主动纠正
2. **某些细节推敲不够**：如 WebUI 是否需要认证问题在 brainstorming 阶段未深入讨论，留到了 SPEC 的"未决问题"中
